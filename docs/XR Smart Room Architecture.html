XR Smart Room architecture

The headset talks only to the bridge on the lab PC. The bridge polls each lab system over its own protocol, keeps the latest state, and pushes every change to XR as one JSON message. The Unity app is still planned; the bridge and everything below it run today.

Deployment

Where each part runs and which protocol connects it. Real devices drive the virtual room: the DALI panel sets the colour and on/off of the virtual ceiling lights, and the dimmer switch sets their brightness.

Bridge server

Inside server.py. One Devices back end is chosen at start: the real lab, or the simulation used with --simulate. Both publish state to the hub, which broadcasts it to XR and runs the UC1 and UC3 rules.

Messages on the WebSocket

// bridge → XR: one state change
{ "device": "dimmer1", "property": "level", "value": 60, "source": "real", "timestamp": "2026-10-13T10:15:00Z" }
// XR → bridge: a command
{ "device": "curtain1", "command": "set_position", "value": 40 }

Notation used

Node «device»
Physical hardware, drawn as a 3D box.
«executionEnvironment»
Software that hosts other software, nested in its node.
«artifact»
A deployed file, such as server.py.
Communication path
Solid line between nodes, labelled with its protocol.
«component» and parts
Replaceable units; parts are named name : Type.
Ball and socket
Provided and required interface, joined in an assembly.
Port
Small square on a component border; arrows inside are delegations.
Dependency, realisation
Dashed open arrow; dashed arrow with hollow triangle.
